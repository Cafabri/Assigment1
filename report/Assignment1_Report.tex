\begin{abstract}
\noindent
The naive O($n^3$) triple-loop matrix multiplication was implemented in Python~3.11,
Java~21 and C (gcc~16.1.0, \texttt{-O2}) with the same \texttt{ijk} loop order, 64-bit
floating point and bit-identical input matrices produced by a common random generator.
All implementations were validated against NumPy and benchmarked on an Intel Core
i7-13700KF (Windows~11) for $n = 10$ to $3000$ under a budget of 15~minutes per run,
with five measured runs after warm-up per configuration. Between $n = 100$ and $1000$
the runtime grows close to $n^3$ in the three languages (fitted exponents 3.2--3.3);
beyond $n = 1000$, when the matrices no longer fit in the 30~MB L3 cache, the compiled
versions grow much faster (exponents 4.6--4.7). C is the fastest at every size. Java
needs 1.2--2.1 times the C time up to $n = 1000$ and up to 5.4 times at $n = 1500$;
Python needs 130--175 times the C time up to $n = 1500$. C and Java completed every
declared size up to $n = 3000$, while Python's largest feasible size was $n = 2000$
(838~s per run). Memory grows as $n^2$ in all three. These results describe these
programs on this computer and should not be generalised to the languages as a whole.
\end{abstract}

\section{Introduction and objective}

\subsection{Motivation}

Matrix multiplication appears in almost every numerical and data-processing
workload~\cite{cormen2009}, and its naive form is short enough to be written in exactly
the same way in different languages. It is therefore a good test case to see how much
the execution environment alone (an interpreter, a JIT compiler or an ahead-of-time
compiler) changes the performance of one fixed algorithm. The measurements obtained here
are also the baseline for the optimised, parallel and distributed versions of the
following assignments.

\subsection{Research question}

\begin{center}
\begin{minipage}{0.88\textwidth}
\itshape How does matrix size affect the runtime and memory usage of a naive triple-loop
matrix multiplication implemented in Python, Java and C, when each language runs in its
standard execution environment?
\end{minipage}
\end{center}

\subsection{Variables}

\begin{itemize}
    \item \textbf{Factors varied:} the matrix size $n$ (side of the $n \times n$
    matrices) and the implementation language.
    \item \textbf{Outcomes measured:} the execution time of the multiplication kernel and
    the memory used by each implementation.
    \item \textbf{Kept fixed:} algorithm and loop order, numeric type (float64), input
    matrices, machine, compiler and runtime settings, single thread.
\end{itemize}

\section{Background}

\subsection{The triple-loop algorithm}

Each element of the result is a dot product, $C[i][j] = \sum_k A[i][k] \cdot B[k][j]$.
With $n^2$ elements and $n$ terms per element, the algorithm always performs $n^3$
multiply-adds, independently of the values, and stores three $n \times n$
matrices~\cite{cormen2009}. Algorithms with a lower asymptotic cost exist, but this
assignment fixes the classical one.

\subsection{Why the time per operation is not constant}

The $n^3$ model assumes that every multiply-add costs the same. On real processors,
reading data from a cache is much cheaper than reading it from main
memory~\cite{hennessy2019}. With the \texttt{ijk} order, $A$ is read row by row, but $B$
is read column by column, jumping $n$ elements between consecutive accesses. While the
matrices fit in a cache level this is cheap; once they do not, many of these accesses
miss the cache and each operation becomes slower~\cite{hennessy2019}. The
i7-13700KF has 2~MB of L2 cache per performance core and 30~MB of shared L3.

\subsection{How each language executes the loop}

\begin{itemize}
    \item \textbf{C} is translated to machine code before execution, so the loop runs
    directly on the processor.
    \item \textbf{Java} starts executing bytecode and the HotSpot virtual machine
    compiles the most frequently executed methods to optimised machine code during the
    run~\cite{oraclejvm}. Early executions are therefore slower, and measurements need
    warm-up runs and repetitions.
    \item \textbf{CPython} executes the bytecode with an interpreter, and every number is
    a separate object with its own type information~\cite{pydatamodel}. Each multiply-add
    therefore involves several interpreted instructions and the creation of a new float
    object.
\end{itemize}

\section{Methodology}

\subsection{Implementations and data layout}

The three kernels follow the \texttt{ijk} order with 64-bit floating-point values
(\texttt{double} in C and Java, \texttt{float} in Python), run on one thread and do not
call any numerical library. The way each language stores a matrix cannot be made
identical:
\begin{itemize}
    \item \textbf{C:} a single flat array of $n^2$ doubles, indexed as $i \cdot n + j$
    (8 bytes per element, fully contiguous).
    \item \textbf{Java:} \texttt{double[][]}, i.e.\ one array per row. Values are stored
    as 8-byte doubles, but each row is a separate object, so reading \texttt{B[k][j]}
    requires following a reference to row $k$ first.
    \item \textbf{Python:} a list of lists. The inner lists hold references (8 bytes) to
    float objects (24 bytes), about 32 bytes per element.
\end{itemize}
In Java and Python the result matrix is created inside the multiplication function, so
its allocation is part of the measured time; in C it is allocated beforehand and only
reset to zero, outside the timer. This adds O($n^2$) work against the O($n^3$) of the
loop, and is negligible except for the smallest sizes.

\subsection{Input data}

To make the three languages multiply exactly the same matrices, the same
pseudo-random generator, SplitMix64, was written in C, Java and Python with identical
constants. Each 64-bit output is converted to a double in $[0, 10)$ by taking its upper
53 bits, scaling by $2^{-53}$ and multiplying by 10; matrices are filled row by row, with
seed 42 for $A$ and 43 for $B$. Every operation of this conversion is exact or correctly
rounded in IEEE~754, so the generated values are bit-identical in the three languages.
This was verified through the checksums described in Section~3.6.

\subsection{Measurement protocol}

A script (\texttt{run\_experiment.py}) compiles the C and Java programs and runs every
configuration in a separate process, one language after another, so that no two
benchmarks run at the same time.
\begin{itemize}
    \item \textbf{Sizes:} $n \in \{10, 50, 100, 200, 300, 500, 750, 1000, 1500, 2000,
    3000\}$, declared before the run and identical for the three languages.
    \item \textbf{Budget:} 15~minutes per individual run and 30~GB of memory. If a run
    exceeds the time limit, the script stops the process, records the configuration as
    TIMEOUT and does not run larger sizes for that language (SKIPPED). No time is
    assigned to these configurations.
    \item \textbf{What is timed:} only the call to the multiplication function; input
    generation happens before the timer starts.
    \item \textbf{Clocks:} all monotonic; C uses the Windows
    \texttt{QueryPerformanceCounter} function, Java uses \texttt{System.nanoTime} and
    Python uses \texttt{time.perf\_counter}. Times are stored in nanoseconds.
    \item \textbf{Warm-up and repetitions:} 2 (C), 3 (Java) and 1 (Python) warm-up runs,
    followed by 5 measured runs. Warm-up runs are kept in the raw data but excluded from
    the statistics. Each configuration is summarised by the median and the interquartile
    range (IQR).
    \item \textbf{Result consumption:} after every run, each program computes the sum of
    all elements of the result (checksum) and writes it with the measurement, so the
    multiplication cannot be skipped by the compiler.
\end{itemize}

\subsection{Memory measurement}

There is no single memory tool that works in the three languages, so each one uses its
own metric:
\begin{itemize}
    \item \textbf{C:} size of the three allocated arrays, $3 \times 8n^2$ bytes
    (computed from the allocation, not measured).
    \item \textbf{Java:} increase of the used heap during the call,
    \texttt{totalMemory()} minus \texttt{freeMemory()}, read after a \texttt{gc()}.
    \item \textbf{Python:} peak traced by \texttt{tracemalloc}, started just before the
    call.
\end{itemize}
Java and Python therefore see only the memory allocated inside the function, which is
the result matrix. Because \texttt{tracemalloc} traces every allocation and slows the
Python kernel down considerably, Python memory is measured in one additional run that
is not used for timing, and only for $n \le 1000$, where that run still fits in the
time budget.

\subsection{Correctness}

Validation was done in three steps before analysing the timings:
\begin{enumerate}
    \item \textbf{Exact cases.} Each program checks, at start-up, the product by the
    identity matrix, by the zero matrix, and
    [[1,2],[3,4]] $\times$ [[5,6],[7,8]] = [[19,22],[43,50]], with exact equality.
    \item \textbf{Reference implementation.} For $n = 50$ and $n = 257$, each program
    writes its full result matrix, which is compared element by element with NumPy's
    \texttt{A @ B} computed on the same matrices. Since all inputs are non-negative,
    the sums have no cancellation and their relative rounding error is bounded by about
    $n u$, with $u = 2^{-53} \approx 1.1 \times 10^{-16}$~\cite{goldberg1991}: about
    $3 \times 10^{-14}$ for $n = 257$ and $3 \times 10^{-13}$ for $n = 3000$. The
    acceptance criterion is a relative error below $10^{-11}$ for every element, more
    than 30 times above that bound, while an indexing error would produce relative errors
    close to 1. No absolute tolerance is needed: every reference element is a sum of $n$
    positive products, so none of them is close to zero.
    \item \textbf{Checksums.} The checksum of every benchmark run is compared across
    runs, across languages and with the checksum of NumPy's result for the same $n$.
\end{enumerate}

\section{Discussion}

\subsection{Evaluation of the hypotheses}

In answer to the research question: memory grows as $n^2$ in the three languages, and
runtime grows as $n^3$ only while the matrices fit in the cache; beyond that size the
time per operation increases and the growth is steeper. The language changes the
runtime by a large factor (Python 75--175 times slower than C), but this factor is not
fixed: the Java--C gap in particular depends on $n$.

\subsection{Growth with matrix size}

The cubic prediction of Table~\ref{tab:predictions} holds only while the matrices fit in
the cache. For $100 \le n \le 1000$ the three implementations grow with exponents between
3.17 and 3.31, and doubling $n$ multiplies the time by 7.0--8.9, close to the factor of 8
of the model. Beyond $n = 1000$ the compiled versions depart strongly from it: from
$n = 1000$ to $2000$ the C time grows 23.5 times and the Java time 40.9 times. The number
of operations still follows $n^3$ exactly, so this extra growth comes from each operation
becoming more expensive, which the $n^3$ model does not capture.

The point where this happens is consistent with the cache sizes. Three matrices of
doubles occupy $24n^2$ bytes: 24~MB at $n = 1000$, which still fits in the 30~MB L3
cache, and 54~MB at $n = 1500$, which does not. In C the cost per operation stays between
0.27 and 0.47~ns up to $n = 1000$ and then rises to 0.57, 1.39 and 2.73~ns at $n = 1500$,
2000 and 3000 (Figure~\ref{fig:costperop}). At these sizes, consecutive accesses to a
column of $B$ are $8n$ bytes apart (16~KB at $n = 2000$), so almost every access needs a
new cache line from main memory~\cite{hennessy2019}. This explanation agrees
with the measurements, but cache misses were not measured with hardware counters, so it
remains a hypothesis.

At small sizes the cubic model does not describe Java either: at $n = 10$ one
multiply-add costs 22~ns, and the first warm-up run at $n = 100$ was six times slower
than the measured median. Both are consistent with fixed overheads and with code that
the JIT compiler has not yet optimised~\cite{oraclejvm}.

\subsection{Differences between languages}

The predicted ranking is correct at every size: C is the fastest, followed by Java and
then Python. The size of the gaps, however, depends on $n$, so no single factor
describes them.

\textit{Java vs C.} For $100 \le n \le 1000$ Java needs 1.2--2.1 times the C time: once
the loop is compiled, both execute native code, as predicted. At $n = 1500$ the gap
jumps to 5.4, because the cost per operation of Java grows from 0.75 to 3.11~ns while
that of C grows only from 0.47 to 0.57~ns. Both store 8-byte doubles, so the amount of
data is the same; the most likely difference is how $B$ is stored. In C, the address of
$B[k][j]$ is computed directly from $k$ and $j$ inside one flat array. In Java, every
step of the inner loop first reads the reference of row $k$ from the outer array and only
then the value, so each operation needs one extra memory access, and the row arrays may
be spread over the heap~\cite{hennessy2019}.
For larger sizes the gap narrows again (1.7 at $n = 3000$), because C also becomes
limited by main memory. The experiment cannot separate the layout from other JIT effects
such as bounds checks; this question is left for Assignment~2. The small drop of the Java
cost per operation at $n = 1000$ (0.75~ns against 0.87~ns at $n = 750$) is not explained
by these data.

\textit{Python vs C.} Python needs 130--175 times the C time up to $n = 1500$. This is
above the predicted range of 10--100, so the prediction is only partly confirmed: the
ranking is right, but the interpreter overhead was underestimated. CPython spends about
45~ns per multiply-add even for small matrices, against 0.3~ns in C, because each
operation goes through the interpreter, checks the types of its operands and creates a
new float object~\cite{pydatamodel}. This fixed cost dominates at every size; Python's
cost per operation increases only gradually with $n$ (45 to 105~ns), and the Python/C
ratio drops to 75 at $n = 2000$ only because C slows down, not because Python gets
faster.

\subsection{Memory}

The quadratic growth is confirmed: the memory divided by $n^2$ is practically constant in
each language (24.0~B in C, 8.1--8.4~B in Java and 32.0--32.2~B in Python for
$n \ge 200$). The absolute values are not comparable, because C counts three matrices and
Java and Python only the result. Comparing the same object, the result matrix, Python
needs 32 bytes per element against 8 in Java and C, i.e.\ four times more, because of the
reference plus the float object. The Java values for $n \le 50$ are dominated by
allocation buffers and the garbage collector and are not meaningful. The largest memory
value, 206~MiB, is far below the 30~GB budget; the only limit reached in the experiment
was the time limit.

\subsection{Limitations}

\begin{itemize}
    \item The study uses a single computer, operating system and set of language
    versions; other hardware, in particular other cache sizes, would move the points
    where the cost per operation increases.
    \item Five repetitions per configuration give only a rough estimate of variability,
    and runs shorter than about 0.1~ms are only a few ticks of the clock.
    \item The memory metric is different in each language, approximate in Java because
    of garbage collection, and available for Python only up to $n = 1000$.
    \item The explanations based on the cache and on the Java row layout are inferred
    from the timings only.
    \item The declared size sequence ended at $n = 3000$, where C and Java still ran far
    below the budget (74~s and 126~s per run). Their actual largest feasible size is
    therefore larger and was not determined.
\end{itemize}

\section{Conclusions}

For the three implementations and the conditions described in Section~3:
\begin{itemize}
    \item Up to $n = 1000$ the runtime agrees with the $n^3$ model (exponents 3.2--3.3).
    From $n = 1500$, once the three matrices exceed the L3 cache, C and Java become much
    slower than the model predicts (exponents 4.6--4.7), so the cost of an operation
    depends on the matrix size and not only on the number of operations.
    \item C is the fastest at every size. Java needs 1.2--2.1 times the C time up to
    $n = 1000$, up to 5.4 times at $n = 1500$, and 1.7 times at $n = 3000$. Python needs
    130--175 times the C time up to $n = 1500$, more than predicted.
    \item Memory grows as $n^2$; for the same result matrix Python uses four times more
    memory than Java or C.
    \item Under the 15-minute budget, C and Java completed every declared size up to
    $n = 3000$, and Python up to $n = 2000$.
\end{itemize}
These results compare specific implementations on one machine; they are not a general
ranking of programming languages. Two questions remain open: whether the jump in the cost
per operation is caused by cache and memory-access effects, and how much of the Java--C
gap comes from the \texttt{double[][]} layout. Both are natural starting points for the
loop-reordering and blocking optimisations~\cite{hennessy2019} of Assignment~2.
