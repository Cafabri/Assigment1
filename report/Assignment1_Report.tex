\section*{Abstract}

This study compares a naive O($n^3$) triple-loop matrix multiplication implemented in
Python~3.11, Java~21 (JVM with JIT) and C (gcc~16.1.0, \texttt{-O2}) across matrix
sizes from $n = 10$ to $n = 1000$. Runtime grows cubically in all three languages.
C is the fastest implementation at every tested size. Java takes approximately 2$\times$
as long as C at $n = 1000$; Python reaches approximately 12~minutes at $n = 1000$,
around 1500$\times$ slower than C. Memory usage scales as O($n^2$) across all
implementations. Results are scoped to the tested hardware, compiler settings and input
sizes.

\section{Introduction and Objective}

Matrix multiplication is a fundamental operation in scientific computing. Its naive
implementation requires O($n^3$) arithmetic operations for $n \times n$ matrices, making
performance differences across languages clearly visible as $n$ grows.

\textbf{Research question:} How does matrix size affect the runtime and memory usage of a
naive triple-loop matrix multiplication implemented in Python, Java and C, when each
language runs in its standard execution environment?

\textbf{Hypothesis:} Runtime will grow cubically for all three implementations. C,
compiled with standard optimisation flags, is expected to be the fastest. Java with JIT
is expected to be close to C. Python, as an interpreted language, is expected to be one
to two orders of magnitude slower than the compiled implementations.

\section{Background}

The standard triple-loop algorithm computes $C[i][j] = \sum_k A[i][k] \cdot B[k][j]$
for all $i$, $j$, performing $n^3$ multiply-accumulate operations. Its theoretical
complexity is O($n^3$) in time and O($n^2$) in space for the output matrix.

The three languages differ fundamentally in how they execute code:

\begin{itemize}
    \item \textbf{Python (CPython):} interpreted line by line. Each operation involves
    dynamic type checking and object overhead, making inner loops expensive.
    \item \textbf{Java (JVM):} compiled to bytecode and then JIT-compiled to native
    machine code at runtime. The JIT identifies hot loops and applies optimisations
    automatically after warm-up.
    \item \textbf{C (gcc \texttt{-O2}):} compiled ahead-of-time to native machine code
    with standard compiler optimisations, including register allocation and instruction
    scheduling.
\end{itemize}

\section{Methodology}

\subsection*{Implementations}

Each implementation uses the same \texttt{ijk} triple-loop order and 64-bit
floating-point arithmetic (\texttt{float} in Python, \texttt{double} in Java and C).
No optimised library calls are used for the multiplication itself. All three
implementations run on a single thread; no internal library threads are created.
Storage layout differs across languages: Python uses a list of lists (each inner list
is a separate heap object); Java uses \texttt{double[][]}, an array of independently
allocated row arrays; C uses a flat one-dimensional array with index $i \cdot n + j$,
providing truly contiguous row-major storage.

\subsection*{Correctness}

Before benchmarking, each implementation verifies three test cases: $A \times I = A$
(identity matrix), $A \times \mathbf{0} = \mathbf{0}$ (zero matrix), and a $2 \times 2$
product with known result ([[1,2],[3,4]] $\times$ [[5,6],[7,8]] = [[19,22],[43,50]]).
All checks passed in all three languages.

The test inputs use small integers (values 0--8), for which floating-point
multiply-accumulate operations produce exact results with no rounding error. Exact
equality (\texttt{==}) is therefore used as the verification criterion. For general
random floating-point inputs, differences in evaluation order may introduce rounding
errors bounded by machine epsilon ($\varepsilon \approx 2.2 \times 10^{-16}$ for
IEEE~754 double precision); these do not affect the benchmarks since correctness is
verified only on the integer-valued test cases.

\subsection*{Budget}

A maximum runtime of 15~minutes per run and a memory limit of 30~GB were declared before
testing large sizes. All configurations up to $n = 1000$ completed within these limits.
$n = 1000$ is both the largest attempted and the largest feasible size under the declared
budget.

\subsection*{Measurement protocol}

\begin{itemize}
    \item \textbf{Sizes tested:} $n \in \{10, 50, 100, 200, 300, 500, 750, 1000\}$.
    \item \textbf{Repetitions:} 5 measured runs per configuration, preceded by warm-up
    runs (1 for Python, 3 for Java, 2 for C) to reduce cold-start effects.
    \item \textbf{Timing:} \texttt{perf\_counter} (Python), \texttt{nanoTime} (Java),
    \texttt{QueryPerformanceCounter} (C). All timers measure wall-clock time of the
    multiplication kernel only; input generation is outside the timed region.
    \item \textbf{Memory:} peak heap via \texttt{tracemalloc} (Python); JVM heap delta
    before and after \texttt{gc()} (Java); allocated matrix storage $3n^2 \times 8$~bytes
    (C — exact, since allocation is explicit).
    \item \textbf{Summary statistic:} median and interquartile range (IQR) over 5
    repetitions.
    \item \textbf{Inputs:} matrices generated with fixed seeds (42 for A, 43 for B) using
    each language's standard PRNG, values in $[0, 10]$. Cross-language PRNGs differ, so
    matrices are statistically similar but not bit-identical.
\end{itemize}

\section{Discussion}

\textbf{Cubic growth.}
All three implementations exhibit clear cubic growth. From $n = 100$ to $n = 200$
(factor of 2), runtimes multiply by approximately 8 ($2^3$), consistent with O($n^3$).
Figure~\ref{fig:costperop} shows the cost per inner-loop operation (median time divided
by $n^3$): a flat line would indicate perfect cubic scaling. For all three languages the
cost per operation rises at large $n$, consistent with cache pressure as the working set
exceeds the L2/L3 cache.

\textbf{C is the fastest.}
C compiled with \texttt{-O2} is the fastest implementation at every tested size. At
$n = 1000$, Java takes approximately $2\times$ as long as C, and Python takes
approximately 1500$\times$ as long. The gap between C and Java is explained by the
difference in storage layout: Java's \texttt{double[][]} stores each row as a separate
heap object, so the inner loop accessing column~$j$ of~$B$ must first load a row
reference, adding an indirection that C's contiguous flat array avoids.

\textbf{Python overhead.}
Python is approximately 1500$\times$ slower than C and 730$\times$ slower than Java at
$n = 1000$. CPython interprets each bytecode instruction individually, performs dynamic
type checks on every operation, and represents numbers as heap-allocated objects.
These overheads dominate the inner loop and explain the large constant factor relative
to compiled implementations.

\textbf{Memory.}
Memory scales as O($n^2$) in all three cases, consistent with storing three $n \times n$
matrices. The different measurement methods produce different absolute values: C reports
exact allocated storage, while Python and Java include object headers and runtime
overhead. These metrics should not be compared as if identical.

\textbf{Limitations.}
Cross-language PRNG differences mean input matrices are statistically similar but not
bit-identical. The Java memory metric is approximate due to GC activity. The C timer
resolution is insufficient to measure $n = 10$ (result below 1~$\mu$s). Results are
specific to the tested hardware, OS and language versions.

\section{Conclusions}

All three implementations exhibit the expected O($n^3$) runtime growth. Under the tested
conditions — each language in its standard execution environment — C (\texttt{-O2})
achieves the lowest execution time, followed by Java (JIT), then Python. Python's
interpreter overhead makes it unsuitable for large-scale naive matrix multiplication
without vectorised libraries. Memory usage scales quadratically in all cases, with
differences in absolute values explained by the measurement method.

These conclusions apply strictly to the tested implementation, hardware and settings.
Cache blocking, loop reordering and further compiler optimisations will be explored in
Assignment~2.
